# Этап 17 — Скан в отдельном процессе (E), пауза обложек в настройках, плейлисты

Версия 0.22.1. Схема `mtr_music` — v5.

## Плейлисты: сборные обложки

Плитки коллажа брали обложки **треков** (`tr-<id>`). Фоновая фаза кеширует обложки **альбомов**
(`al-<id>`), поэтому ключи треков в кеше не появлялись и плитки не загружались.
Теперь коллаж строится из `album_id` треков (в ответ API добавлено поле `album_id`),
плитки — обложки альбомов, которые фаза уже кеширует. Отдельная обложка трека в списке
тоже берётся из альбома.

## Скан в отдельном процессе (вариант E)

Веб-сервер и тяжёлая работа больше не делят соединение с БД и event loop.

- `app/worker/runtime.py` — цикл worker-процесса: скан, наблюдатель за папкой и фаза обложек.
- `app/worker/__main__.py` — точка входа `python -m app.worker`. Завершается по SIGTERM
  и сам, если веб-процесс исчез (нет сирот).
- `app/worker/supervisor.py` — веб запускает worker дочерним процессом, перезапускает с паузой
  (1, 2, 5, 10, 30 с), не запускает второй, если уже есть живой.
- `app/worker/ipc.py` — каналы связи:
  - **команды** — таблица `worker_commands` (миграция v5): веб пишет `scan` / `reload`,
    worker читает и помечает `handled_at`;
  - **статус** — `DATA_DIR/worker_status.json`, атомарная запись (`os.replace`), heartbeat
    внутри файла; веб считает worker живым, если heartbeat свежее 5 с;
  - **активность** — `DATA_DIR/activity.stamp`: веб трогает файл не чаще раза в секунду,
    worker смотрит mtime. Без блокировок БД на каждый запрос.

Эндпоинты:
- `POST /api/web/scan` — ставит команду, отвечает 202. Без живого worker — 503. Пока идёт скан — 409.
- `GET /api/web/scan/status` — статус из файла worker-а + последний проход из БД.
- `POST /api/web/settings` — после изменения ставит `reload`: worker перечитывает настройки.
- Subsonic `startScan` и WebSocket-статус наблюдателя — через ту же очередь и статус.

## Два новых параметра (в настройках, без .env)

- `cover_active_window_sec` (по умолчанию 3, диапазон 1–60) — окно активности: сколько секунд после
  последнего действия фаза обложек ждёт.
- `cover_max_wait_sec` (по умолчанию 30, диапазон 5–600) — предельное ожидание одного альбома.

Оба применяются без перезапуска: worker читает их при `reload`. Раздел «Настройки» показывает их
в блоке параметров. Упоминания `.env` в интерфейсе заменены на `docker-compose.yml`.

## Проверки

- `tests/test_worker.py`: команда скана выполняется в worker и публикует статус; неизвестная
  команда отклоняется; скан не запускается дважды; атомарность статуса; свежесть heartbeat;
  файловая активность; применение параметров паузы из настроек; веб отказывает без worker (503),
  ставит команду при живом; параметры обложек редактируются через API.
- Сквозная проверка: отдельный процесс `python -m app.worker` просканировал 480 файлов
  (`completed`, 0 ошибок за 1.5 с) и корректно завершился по SIGTERM.
- Полный pytest, headless JS, selfcheck, pyflakes.

## Что изменилось для эксплуатации

- В контейнере теперь два процесса: веб (родитель) и worker (дочерний). Логи идут в один поток.
- Если worker падает, веб перезапускает его сам. Веб-интерфейс покажет, что служба сканирования
  недоступна, если heartbeat устарел.

## Не проверено

- Работа на NAS и с реальной библиотекой под нагрузкой.
- Поведение в браузере во время скана (интерфейс опрашивает тот же статус, но из файла).
- Перезапуск контейнера с работающим скан: команда, помеченная в обработку, но не завершённая,
  при старте не переигрывается; состояние скана закрывается как прерванное (close_stale_runs).

## Что найдено при интеграционной проверке (0.22.1)

- **Дочерний worker не видел настроек веба.** Супервизор запускал `python -m app.worker` с
  переменными окружения, а не с путями из `Settings`. Если настройки переданы в код (тесты,
  нестандартный запуск), worker открывал `/data` и падал с кодом 1, а супервизор перезапускал его
  по кругу. Исправлено: супервизор передаёт все пути и ключ явно (`MUSIC_DIR`, `DATA_DIR`,
  `USERS_DB`, `MUSIC_DB`, `COVERS_DIR`, `MTR_SECRET_KEY_FILE`, `MTR_SECRET_KEY`).
- Тест сквозного пути (`tests/test_worker_integration.py`) это поймал: без него ошибка была бы
  видна только на устройстве.

## Что проверено автоматически

- Супервизор поднимает живой worker (heartbeat) и после `stop()` не оставляет процесс.
- Плейлист отдаёт `album_id` у каждого трека (нужно для сборных обложек).
- Полный pytest, headless JS, selfcheck, pyflakes.

## Что НЕ проверено

- Полный сквозной прогон через запущенный uvicorn (вход → скан → статус → остановка сервера)
  выполнен частично: скан через HTTP проходит (202, `completed`, 480 файлов), но в той сессии
  не удалось остановить тестовый сервер, поэтому проверка сирот через живой сервер не завершена.
  Проверка сирот выполнена тестом супервизора, а не через uvicorn.
- Сборка образа и запуск в контейнере на arm/v7 и на NAS.
- Поведение интерфейса в браузере во время скана и на сборных обложках плейлистов.
