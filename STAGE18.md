# Этап 18 — Навигация, настройки скана, установка

Версия 0.23.0.

## Интерфейс

- **Хлебные крошки вместо «назад».** В альбоме: Библиотека / Альбомы / <название>. Первая крошка
  с иконкой стрелки, последняя — не ссылка. Та же схема на странице исполнителя.
  Отступы у крошек: 18px сверху, 22px снизу (CSS `.breadcrumbs`).
- **Исполнитель в альбоме — ссылка** на список его альбомов. Без подчёркивания и цвета ссылки,
  подсветка только при наведении (`.artist-plain-link`). Для этого эндпоинт альбома отдаёт `artist_id`.
- **Обложки треков в альбоме.** Треки запрашивали `tr-<id>`, а фон кеширует `al-<id>` — поэтому
  не грузились. Теперь каждый трек получает `album_id` и обложку своего альбома.
- **Форма создания администратора.** Карточка шире: 576px вместо 384px (в 1.5 раза). Поля разнесены:
  группа = подпись + поле с отступом 8px, между группами 20px, сами поля растянуты на всю ширину
  и выше (46px). Подсказка о длине пароля.
- **«Загрузка…» → «Загрузка / Идёт сканирование… N%».** Заглушка списков учитывает идущий скан.
  Полная строка с процентом и этапом — только в разделе «Сканирование».
- **Ошибка сети.** Вместо «failed to fetch» — понятный текст; для GET один автоматический повтор.
- **Главная:** убраны кнопка «Пересканировать» и плашка «Пользователей».
  Количество пользователей — строкой во вкладке «Сервер».
- **Кнопки обложек** («Пересканировать обложки», «Очистить кэш обложек») перенесены
  из «Сервера» в «Сканирование».

## Сканирование

- Новая настройка `scan_batch_tracks`: сколько треков обрабатывать за заход. 0 — все сразу
  (по умолчанию). Заходы идут строго последовательно: следующий начинается после записи предыдущего.
- Новый эндпоинт `POST /api/web/covers/warm` — ставит worker-у команду запустить фазу обложек.

## Производительность списка альбомов

Запрос списка альбомов считал `COUNT(*)` по трекам подзапросом на каждый альбом, а `count_albums`
обходил всю таблицу при каждой загрузке страницы. На 2400 альбомах и 24000 треках:
страница 10 448 мс → 13 мс, подсчёт 8307 мс → 7 мс. Результаты для всех сортировок совпадают.
Это и было причиной зависшей «Загрузки…» и таймаутов на большой библиотеке.

## Docker и установка

- `docker-compose.yml`: комментарий с вариантами путей, включая `D:/music_temp:/music:ro` и `D:/data:/data`.
- `install-in-docker.sh` в корне: объединяет сборку и самопроверку, проверяет требования
  (Docker, Compose v2, память 512 МБ, диск 1 ГБ, архитектура) с вопросом «продолжить? (y/N)»,
  спрашивает про удаление `covers` (y/n), ждёт `/healthz`, проверяет heartbeat worker-а.
- `scripts/clean-rebuild.sh` удалён, `scripts/selfcheck.sh` оставлен: его вызывает установщик
  и он же доступен как `docker exec mtr-app sh /app/scripts/selfcheck.sh`.

## Проверено

- Сравнение старого и нового запросов альбомов на одинаковых данных (4 сортировки + подсчёт).
- Синтаксис `install-in-docker.sh` (`sh -n`), ветки вопросов: отказ от установки по требованиям,
  удаление `covers` с сохранением баз.
- Полный pytest, headless JS, pyflakes, selfcheck.

## Не проверено

- Вид интерфейса в браузере: крошки, ссылка на исполнителя, форма администратора, обложки треков.
- Запуск `install-in-docker.sh` против реального Docker: в песочнице Docker нет.
- Работа на NAS и на большой библиотеке.
