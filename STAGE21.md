# Этап 21 — Идентификаторы больше 10 000 в Subsonic API

Версия 0.23.3.

## Симптом

В клиенте все треки с id больше 10 000 показывались как один и тот же трек.

## Причина

`app/subsonic/router.py`, функция `_int_param`:

```python
def _int_param(value, *, default, name, minimum=0, maximum: int = 10_000):
    ...
    return max(minimum, min(parsed, maximum))
```

Потолок 10 000 был значением **по умолчанию** и применялся ко всем параметрам,
включая `id`. Любой идентификатор выше лимита молча обрезался до 10 000:

```
id= 9999 -> 9999
id=10001 -> 10000     ← баг
id=10500 -> 10000     ← баг
id=99999 -> 10000     ← баг
```

Это ровно вариант «clip»: ошибки нет, исключения нет, сервер считает, что всё в порядке,
и отдаёт чужой трек. Отсюда и «слипание» — все запросы за пределами лимита приходили
на один и тот же id 10000.

Затронуты были все методы с параметром `id`: `getArtist`, `getAlbum`, `getSong`,
`stream`, `download`, `getCoverArt`.

## Что исправлено

- Потолок больше не применяется по умолчанию (`maximum: int | None = None`).
- Явные ограничения остались только там, где они по смыслу нужны: `size` (500),
  `offset` (100 000), `artistCount` / `albumCount` / `songCount` (`MAX_SEARCH_COUNT` = 500).
- Вторая версия `search` (`/rest/search`) раньше вообще не ограничивала счётчики —
  теперь у неё тот же предел `MAX_SEARCH_COUNT`, что и у `search3`. Без ограничения
  клиент мог запросить `songCount=1000000` и заставить сервер собрать ответ на миллион
  записей.
- Минимум и значения по умолчанию работают как раньше.

## Проверено

- `tests/test_subsonic.py`:
  - `test_high_track_id_is_not_clipped` — трек с реальным id 10501 запрашивается через
    `/rest/getSong.view` и возвращается с тем же id и правильным названием;
  - `test_high_album_and_artist_ids_are_not_clipped` — то же для альбома (30001)
    и исполнителя (20001);
  - `test_id_param_has_no_default_ceiling` — прямой тест разбора: id проходит без
    искажений, явный потолок для `size` продолжает работать.
- Ручная проверка на базе: трек с id 10501 находится по своему id, а не по 10000.
- Полный pytest, pyflakes.

## Другие проверенные версии причины

Разбирались и отброшены — в коде сервера их нет:

- **Переполнение массива фиксированного размера.** В Python массивов фиксированной длины
  нет, а id нигде не используются как индексы списков. Идентификаторы везде — значения
  из `AUTOINCREMENT` и строки в JSON.
- **Округление по модулю.** Оператора `%` над id в проекте нет.
- **Конфликт локальной и облачной базы.** Локальной таблицы соответствия и «дефолтного
  идентификатора 10000» не существует: сервер отдаёт ровно то, что лежит в базе.
- **Обрезка при разборе ключей обложек.** Ключи `al-<id>` / `tr-<id>` формируются
  в `format.py` простым `f"{kind}-{entity_id}"`, обратный разбор идёт в веб-API без
  ограничений.

То есть причина была одна, и она на сервере, а не в клиенте.

## Что стоит проверить у себя после обновления

1. Полностью пересканировать библиотеку не нужно — id не меняются.
2. В клиенте (Arpeggi) очистить кеш и пересинхронизировать библиотеку: он мог
   закешировать «слипшиеся» записи с id 10000.
3. Если после обновления часть треков всё ещё показывает не то — проверить, что клиент
   ходит именно на этот сервер, и посмотреть в журнале, какие `id` он запрашивает:
   `docker logs mtr-app | grep getSong`.
