# Этап 22 — Раздел «Исполнители» в Subsonic-клиентах

Версия 0.23.4.

## Симптом

В клиенте (Arpeggi) не открывался раздел исполнителей — пусто или ошибка.
Альбомы, плейлисты, поиск и воспроизведение при этом работали.

## Причина

Два метода, которые клиенты вызывают при открытии раздела исполнителей, не были
реализованы вовсе:

```
getMusicDirectory  404 {"detail":"Not Found"}
getArtistInfo2     404 {"detail":"Not Found"}
```

404 приходил в формате FastAPI (`{"detail": ...}`), а не в конверте Subsonic.
Клиент рассчитывает разобрать `subsonic-response`, разбор падает — и раздел
показывается пустым. Остальные разделы работают, потому что их методы есть.

Дополнительно: `getTopSongs`, `getLyrics`, `getRandomSongs`, `getAlbumInfo2` и ещё
десяток методов тоже отдавали 404. Сами по себе они не критичны, но любой клиент,
который их пробует, получал невалидный ответ.

## Что исправлено

**`getMusicDirectory`** — обход библиотеки «по папкам» для старого ID3-режима.
Папка альбома отдаёт свои треки, папка исполнителя — свои альбомы.

Пришлось решить проблему, которой не было видно сразу: у нас плоская библиотека,
и id исполнителя с id альбома лежат в одном числовом пространстве. Исполнитель 1
и альбом 1 — разные сущности с одинаковым числом, а клиент присылает только число.
Первая версия метода отдавала треки вместо списка альбомов именно из-за этого.

Решение: `getIndexes` отдаёт id исполнителей со сдвигом `FOLDER_ARTIST_OFFSET`
(1 000 000 000), а `getMusicDirectory` по такому id понимает, что просят альбомы
исполнителя. Обычные id трактуются как альбомы — как и раньше. Сдвиг невидим
пользователю и не меняет id в базе.

**`getArtistInfo` / `getArtistInfo2`** — валидный пустой ответ (биография, похожие,
картинки). Внешних источников у нас нет, но 404 здесь ломал открытие исполнителя.

**Методы без данных** (`getTopSongs`, `getSimilarSongs`, `getSimilarSongs2`,
`getLyrics`, `getLyricsBySongId`, `getRandomSongs`, `getAlbumInfo`, `getAlbumInfo2`,
`getChatMessages`, `getBookmarks`, `getPlayQueue`, `getShares`, `getPodcasts`,
`getInternetRadioStations`) — пустой, но валидный ответ Subsonic.

Перечислены явно, а не перехватом `/rest/*`: перехват перекрыл бы `getCoverArt`,
который регистрируется отдельным роутером ниже. Это не гипотеза — я так сделал
сначала, и обложки начали отдавать пустой JSON вместо картинки. Тест
`test_cover_art_still_works_alongside_new_methods` фиксирует этот случай.

## Проверено

- `tests/test_subsonic.py`, шесть новых тестов:
  - `getMusicDirectory` по id альбома отдаёт его треки;
  - `getMusicDirectory` по id из `getIndexes` отдаёт альбомы, а второй шаг обхода —
    треки (полный путь клиента);
  - неизвестный id — ошибка Subsonic (код 70) с HTTP 200, а не 404 FastAPI;
  - `getArtistInfo2` и `getArtistInfo` отвечают `ok`;
  - методы без данных отдают валидный конверт;
  - обложки продолжают отдаваться картинкой.
- Сквозная проверка: `getIndexes` → папка исполнителя → альбом → треки; обложка
  отдаётся как `image/jpeg`, 2452 байта.
- Полный pytest, pyflakes, headless JS, selfcheck.

## Что проверить у себя

Пересканировать библиотеку не нужно. В клиенте достаточно обновить раздел
исполнителей (или очистить кеш, если он закешировал пустой список).

## Осталось нереализованным

Возвращаются пустыми, а не работают по-настоящему: похожие исполнители, топ треки,
тексты песен, закладки, очередь воспроизведения на сервере, общие ссылки, подкасты,
интернет-радио. Если что-то из этого нужно — это отдельная задача, а не баг.
