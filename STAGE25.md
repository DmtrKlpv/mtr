# Этап 25 — Медленный getArtists на большой библиотеке

Версия 0.23.8.

## Причина

Запросы по исполнителям (`_LIVE_LINKS`) содержали коррелированный `EXISTS` по таблице
треков для каждого альбома. На 8000 альбомах это тысячи вложенных проходов. Статистика
SQLite (`ANALYZE`) сама по себе проблему не решала: план оставался плохим.

## Что сделано

- `_LIVE_LINKS` переписан: треки и альбомы объединяются через `JOIN` по индексам,
  без коррелированного подзапроса.
- Версия схемы `mtr_music.db` — 6. При обновлении выполняется `ANALYZE`.
- После скана вызывается `PRAGMA optimize`.
- Тест миграции обновлён на версию 6.

## Замер (20 000 треков, 2000 исполнителей, 8000 альбомов)

| Запрос | Было | Стало |
|---|---|---|
| list_artists (все исполнители) | 3.7–6.6 с | 26 мс |
| count_artists | — | 19 мс |
| get_artist | — | 38 мс |
| artist_albums | — | 82 мс |
| search_artists | — | 21 мс |

## Проверено

Полный pytest, pyflakes, headless JS.

## Что сделать у себя

Пересканировать библиотеку не нужно. Обновить сервер: при первом запуске версии 0.23.8
база выполнит `ANALYZE` один раз. Очистить кеш клиента, если он держит старый ответ.
