# Этап 6 — Веб-интерфейс и полное управление сервером

## Страницы
| Путь | Назначение |
|---|---|
| `/login` | форма входа |
| `/app` | оболочка SPA (требует сессию) |
| `/` | редирект на `/app` или `/login` |
| `/static/*` | JS и CSS, белый список файлов |

## Управление (полное)
- **Библиотека**: альбомы, обложки, поиск, прослушивание, скачивание.
- **Плейлисты**: создание, удаление, публикация.
- **Пользователи** (admin): создание, роли, блокировка, сброс пароля, удаление.
- **Сервер** (admin): версия, схема БД, пути, состояние наблюдателя,
  число обложек, пересканирование, очистка кэша обложек.
- **Аккаунт**: смена своего пароля, список и отзыв своих сессий.

## Безопасность
- Сессии: случайный токен в cookie, в БД только SHA-256.
- CSRF обязателен для POST/PUT/PATCH/DELETE, сравнение за постоянное время.
- Обычный пользователь не видит админ-разделы (кнопки скрыты И API
  возвращает 403 — UI-скрытие не является защитой).
- Нельзя удалить себя и нельзя снять роль с последнего админа.
- Блокировка и смена пароля отзывают все сессии пользователя.
- Статика отдаётся по белому списку: `../main.py` → 404.
- Вход защищён тем же троттлингом, что Subsonic: 10 неудач / 5 мин.

## Исправлено по ходу
**Плеер не мог играть.** `/stream` требовал Subsonic-параметры, а браузер
их не имеет — только cookie. Добавлена зависимость `require_auth_or_session`:
сначала проверяются `u/t/s`, затем сессия. Subsonic-клиенты не затронуты.

**Миграция v2.** Таблица `sessions` уже существовала в v1 с другим набором
колонок (`id TEXT`, `ip_address`, без `token_hash`). `CREATE TABLE IF NOT
EXISTS` молча ничего не делала. Переписано на `DROP TABLE` + новая схема.

## Проверено
- 396 тестов.
- Живой сценарий: редирект → вход → `/app` → API → создание пользователя
  с CSRF → 403 без CSRF → статика → выход.

## Ограничения
- Нет редактирования тегов и загрузки файлов.
- Плеер без очереди и плейлистов в UI (API есть).
- Прогресс скана не выведен в UI, только `/ws/scan`.
- Интерфейс минимальный: без drag&drop, без виртуализации длинных списков.

## Исправление v0.6.1: пустые разделы в интерфейсе

Две ошибки в `app/web/static/app.js`, обе видел пользователь:

**1. «card is not defined»** — функция `card()` вызывалась четыре раза
(карточки статистики в «Библиотеке»), но ни разу не была объявлена.

**2. «Cannot read properties of undefined (reading 'count')»** — следствие
более серьёзного расхождения: сервер отвечает конвертом
`{"ok": true, "data": {...}}`, а **все 20 вызовов** в JS ждали данные
напрямую. `stats.tracks` был `undefined`, `info.covers` — тоже.
Исправлено в одном месте: `api()` теперь разворачивает конверт.

**Почему не поймали тесты.** Python-тесты проверяли API и не исполняли JS.
Синтаксическая проверка (`node --check`) такие ошибки не видит — это не
синтаксис, а отсутствующие имена.

Добавлен `tests/js/headless.js`: запускает настоящий `app.js` в `vm`
с подменённым DOM и fetch, вызывает каждый раздел и проверяет, что
отрисовались ожидаемые строки. Запуск: `node tests/js/headless.js`.

Попутно `setView()` стал возвращать промис — иначе нельзя дождаться
отрисовки ни в тестах, ни в вызывающем коде.

## Этап 6.2 (v0.6.2): плейлисты, избранное, добавление треков

Добавлено в интерфейс:
- Страница плейлиста: треки, «▶ Играть всё», переименование, удаление трека.
- Кнопка «＋» у каждого трека: добавление в выбранный плейлист.
- Вкладка «Избранное»: звёздочка у каждого трека, отметка сохраняется
  для каждого пользователя отдельно.
- Смарт-плейлисты показываются, но состав в них не редактируется.

Серверные эндпоинты (всё через сессию + CSRF):
- GET    /api/web/playlists/{id}              — состав; чужой приватный → 404
- POST   /api/web/playlists/{id}/tracks       — добавить track_ids
- DELETE /api/web/playlists/{id}/tracks/{tid} — убрать трек
- POST   /api/web/playlists/{id}/rename
- GET    /api/web/starred, /api/web/starred-ids
- POST   /api/web/tracks/{id}/star            — {"starred": true|false}

Проверка: tests/test_web_playlists.py (10 тестов, включая права доступа),
tests/js/headless.js (страницы плейлиста, избранного, отправка звёздочки).

Не входит в этот шаг: переключение треков и обложки — по решению пользователя
отложены на следующий шаг.

## Этап 6.3 (v0.7.0): фавикон и иконки приложения

Иконка по исходному изображению (жёлтый фон, семь... шесть чёрных полос):
- `icon.svg` — векторный источник, 6 полос с высотами 86/184/300/370/216/120
  (совпадают с замером растрового варианта и с оригиналом);
- `favicon.ico` (16, 32, 48, 64), `favicon-32.png`, `apple-touch-icon.png` (180),
  `icon-192.png`, `icon-512.png`;
- `manifest.webmanifest` — установка как приложение на телефон/десктоп.

Подключение: `<link rel="icon">` и `apple-touch-icon` и `manifest` на обеих
страницах. Корневой `/favicon.ico` отдаётся явно: браузеры запрашивают его
сами, даже без ссылки в HTML.

Проверка: tests/test_favicon.py — файлы, размеры PNG, валидность manifest,
MIME-типы, корневой favicon, CSP не блокирует иконки.
