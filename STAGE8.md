# Этап 8 — Отзывчивость интерфейса и таблица ошибок

Версия 0.15.0. Тема этапа: убрать причину зависания главной на «Загрузка /
Обновление базы…», показать ошибки сканирования таблицей и отдавать данные
по мере просмотра, а не «всё сразу».

## 1. Почему висела главная

Строка «Загрузка / Обновление базы ...» — статический placeholder в
`app/web/templates.py`. Она не исчезала, потому что JS не доходил до
отрисовки: сервер не отвечал.

Причина — обложки. `getCoverArt` → `CoverRepository.for_album()` →
`extract_cover()` читал файл и разбирал ID3/FLAC-картинку **прямо в
async-обработчике**, без выноса в поток. Пока шло чтение, стоял весь event
loop: не отдавался ни `app.js`, ни `/api/web/stats`. Браузер держит до 6
соединений на хост — все шесть занимали обложки, и интерфейс не грузился.

Усугубляло два обстоятельства:

* `for_album` перебирал до 50 треков альбома, пока не найдёт картинку;
* результат «картинки нет» нигде не запоминался — при каждом заходе всё
  повторялось.

### Что сделано

* чтение и запись файлов обложек вынесены в `asyncio.to_thread`;
* `COVER_EXTRACT_CONCURRENCY = 2` — параллельных извлечений не больше двух;
* отрицательный кеш (`NEGATIVE_CACHE_LIMIT = 20 000`) на ключи `al-<id>`:
  альбом без картинки больше не перечитывается. Сбрасывается через
  `forget_missing()` — при очистке кеша обложек;
* порядок поиска выбран по стоимости: сначала `cover.jpg` в каталоге (одно
  чтение каталога), затем встроенные обложки и только у треков с
  `has_cover = 1`, где наличие картинки уже подтверждено при скане.

Замер на синтетической библиотеке с искусственно медленным извлечением
(50 мс на файл): 20 альбомов за 0.52 с, тиков event loop 50 из ожидаемых
52. До правки было бы 0–1 тик — сервер стоял бы всё это время.

## 2. Ошибки сканирования — таблицей

Раньше ошибки хранились склеенной строкой `«путь: причина»` и выводились
в свёрнутом `<details>`, а на странице скана — только числом.

Теперь в `app/repositories/tracks.py` есть `ScanError` с полями `path` и
`reason`, а `ScanCounters.add_error(path, reason)` пишет структуру. В БД
(`scan_runs.errors_json`) лежит список объектов
`{"path": ..., "reason": ...}`.

Причина хранится отдельно от пути не для красоты: текст ошибки сам может
содержать двоеточия (`FLACNoHeaderError: '/music/a.flac' is not a valid
file`), и разбирать склеенную строку обратно — источник ошибок.

Таблица «Файл / Причина» выводится **сразу, без раскрытия**, в трёх местах:

* история скана (`renderScan`);
* текущий проход на странице скана (`updateScanView`);
* панель статуса на главной (`drawScanStatus`).

Прокрутка ограничена (`max-height: 320px`, липкая шапка) — при массовом
сбое строк бывают сотни. Длинные пути переносятся по любому месту
(`word-break: break-all`), иначе таблица расползается по горизонтали.

Записи, сделанные до перехода на структуру, по-прежнему читаются: разбор
старого формата делается в API (`_scan_errors`), а не в интерфейсе.

## 3. Данные по мере просмотра

Главная раньше ждала `/api/web/stats` и только потом рисовала хоть
что-то. Теперь каркас (приветствие, поиск, переключатель) выводится сразу,
а дальше идут три независимых запроса:

* счётчики (`loadStats`);
* «Недавно добавленные»;
* «Недавно прослушанные».

Каждый заполняет свою часть по готовности: медленный больше не задерживает
остальные. Раньше секции ждали друг друга через `Promise.all`.

### Постраничная выдача

`renderAlbumsInto` вызывал `/api/web/albums` без параметров, получал
`limit=100` по умолчанию и резал результат через `slice(0, 300)`. То есть
**из 9289 альбомов было видно только 100**, остальные недоступны
принципиально. Теперь — страницами по 60, кнопка «Показать ещё» и честная
строка «Показано 60 из 9289».

Для этого в ответ `/api/web/albums` добавлены `total`, `limit`, `offset`.

### N+1 в исполнителях

`/api/web/artists` для каждого исполнителя отдельно вызывал
`first_album_id()` — запрос с подзапросом `COUNT(*)` по таблице треков.
На 5254 исполнителях это тысячи обращений в SQLite подряд.

Заменено на `artist_album_map(ids)` — один запрос `GROUP BY` на всю
страницу. Замер на 3000 исполнителей и 18000 треков:

| | время |
|---|---|
| было (N+1, экстраполяция на 5254) | ~27.7 с |
| стало (страница 60 + карта одним запросом) | **9 мс** |

Список исполнителей тоже стал постраничным (`limit`/`offset`, `total`),
пустые исполнители отфильтровываются в SQL через `EXISTS`, а не в Python
после выборки всех строк.

### Ленивые обложки

`<img loading="lazy">` экономит не всё: браузер начинает запрос заранее и
держит несколько соединений. А каждый промах кеша на сервере — это чтение
файла и разбор тегов.

Поэтому `src` выставляется `IntersectionObserver` с запасом 300 px: до
подхода к экрану в разметке стоит заглушка, запроса нет вообще.

## 4. Проверка сканера

* **Зависшие `running`-записи.** Если контейнер убили во время скана,
  запись в `scan_runs` оставалась `running` навсегда, и интерфейс по ней
  решал, что скан идёт, показывая прогресс, которого нет. При старте такие
  записи закрываются методом `close_stale_runs()` как `failed` с причиной
  «прервано: сервер остановлен во время скана».
* **Список ошибок в памяти ограничен** (`MAX_STORED_ERRORS = 500`). При
  массовом сбое (отвалился сетевой том) счётчик `failed` остаётся полным,
  но хранится только срез — иначе список растёт до десятков тысяч строк.

## Что НЕ менялось

Механизм переименований и удалений файлов оставлен как есть — это
отдельная задача. Идентичность трека по-прежнему определяется путём,
`content_hash` в схеме объявлен, но не заполняется. Переименованный файл
помечается `missing` и добавляется как новый трек с новым id, из-за чего
выпадает из плейлистов. Разбор этого — следующий этап.

## Проверка

* **Python:** `python -m pytest --ignore=tests/e2e` — 482 теста, exit code 0
  (было 463, добавлено 19).
* **JS (headless):** `node tests/js/headless.js` — все проверки пройдены.
* **E2E в браузере** (`tests/e2e`) требуют поднятого сервера, не запускались.

## Что не проверено

* Вид таблиц и сеток в настоящем браузере: JS-тесты проходят, но глазами
  не смотрел. При проблемах с вёрсткой правится в `style.css`.
* Поведение на реальной библиотеке 35879 треков / 9289 альбомов /
  5254 исполнителя моделировалось синтетикой. Причина блокировки устранена
  структурно — обложки больше не исполняются в event loop, — но абсолютные
  тайминги на ARM будут иными.

## Замечание про первый запуск

Кеш обложек пуст после чистки, поэтому первые экраны читают файлы. Теперь
это два параллельных чтения вместо сотни, сервер отвечает на остальные
запросы, и картинки доезжают по мере прокрутки. Дальше — из кеша.
